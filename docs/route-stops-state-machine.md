# Route Stops State Machine and Invariants

## Overview

The unified route stop model combines delivery and pickup operations into a single driver execution unit. Each stop represents one client location on a specific route date, and may include both delivery items and pickup items.

## State Machine

### Route Stop Status

The `route_stops.status` field follows this state machine:

```
queued → in_progress → completed
                      → completed_with_exceptions
                      → unable_to_complete
```

**Allowed Transitions:**
- `queued` → `in_progress` (when driver starts the stop)
- `queued` → `unable_to_complete` (if stop cannot be executed)
- `in_progress` → `completed` (normal completion)
- `in_progress` → `completed_with_exceptions` (completion with disputes/exceptions)
- `in_progress` → `unable_to_complete` (if stop cannot be completed)

**Terminal States:** `completed`, `completed_with_exceptions`, `unable_to_complete` (no further transitions allowed)

### Route Stop Item Status

The `route_stop_items.status` field tracks individual item verification:

```
pending → verified
       → disputed
       → exception
       → skipped
```

**Allowed Transitions:**
- `pending` → any other status
- `verified` → `disputed` or `exception` (for corrections)
- Terminal states: `disputed`, `exception`, `skipped` (cannot transition away)

## Completion Invariants

### Completed Status

A stop can transition to `completed` only when:

1. **Signature Required:** `route_stops.signature_data_url` must be set (not NULL)
2. **All Items Verified:** Every `route_stop_items` must have `status IN ('verified', 'skipped')`
3. **At Least One Item:** The stop must have at least one item

**Database Enforcement:** The `validate_route_stop_completion()` function enforces these rules via trigger.

### Completed with Exceptions Status

A stop can transition to `completed_with_exceptions` only when:

1. **Signature Required:** `route_stops.signature_data_url` must be set (not NULL)
2. **All Items Resolved:** Every `route_stop_items` must have `status IN ('verified', 'skipped', 'disputed', 'exception')`
3. **At Least One Exception:** At least one item must have `status IN ('disputed', 'exception')`
4. **At Least One Item:** The stop must have at least one item

### Unable to Complete Status

A stop can transition to `unable_to_complete` when:

1. **Exception Code Required:** `route_stops.exception_code` must be set (not NULL)
2. **Stop-Level Event:** A stop-level event should be logged explaining why completion is not possible

## Stop Generation

The `build_route_stops_for_date(target_date)` function automatically creates stops from:

1. **Delivery Lists:** For each `delivery_list_items` where:
   - `delivery_list.target_date = target_date`
   - `delivery_list.status IN ('confirmed', 'checked_out')`
   - `delivery_list_items.confirmed_for_delivery = true`
   - Creates one stop per `client_id`, groups all delivery items

2. **Pickup Requests:** For each `pickup_request` where:
   - `scheduled_date = target_date`
   - `status = 'assigned'`
   - `assigned_driver_id` is set
   - Attaches pickup items to the same stop (if delivery exists) or creates new stop

**Idempotent:** The function can be run multiple times safely. It uses `ON CONFLICT` to update existing stops and skips items that already exist.

## Row Level Security (RLS)

### Drivers

- **SELECT:** Can view stops assigned to them for today ± 1 day
- **INSERT:** Cannot directly create stops (generated by function)
- **UPDATE:** Cannot directly update stops (must use events)
- **Events:** Can INSERT `route_stop_events` for stops assigned to them

### Internal Roles (admin/office/checkin_staff)

- Full CRUD access to all stops, items, and events
- Can manage disputes

### Portal Users

- No access to route stops (stops are driver-only)
- Can SELECT disputes for their own client

## Event-Driven Architecture

Drivers interact with stops through events (for offline-first operation):

- `STOP_STARTED` → Sets `status = 'in_progress'`, `started_at = now()`
- `SIGNATURE_SET` → Sets `signature_data_url`
- `ITEM_VERIFIED` → Sets item `status = 'verified'`
- `ITEM_EXCEPTION` → Sets item `status = 'exception'`
- `ITEM_DISPUTED` → Sets item `status = 'disputed'`, creates dispute record
- `STOP_COMPLETED` → Validates invariants, sets `status = 'completed'`, `completed_at = now()`

Events are idempotent via `offline_event_id` unique constraint.

## Audit Logging

Status changes are automatically logged to `communication_events` table with:
- `event_type = 'route_stop_status_changed'`
- `subject = 'Route stop status changed'`
- `body` includes old and new status

## Disputes

Two types of disputes:

1. **refused_delivery:** Customer refuses delivery at time of delivery
   - Rug stays in `ready` status (not `picked_up`)
   - Dispute record created with `type = 'refused_delivery'`

2. **post_delivery_claim:** Customer claims issue after delivery
   - Rug remains `picked_up` status
   - Dispute record created with `type = 'post_delivery_claim'`
