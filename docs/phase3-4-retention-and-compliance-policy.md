# Phase 3.4 — Retention and Compliance Policy

## Goal
Define and operationalize retention windows for operational events, payment attempts, and generated artifacts.

## Scope
This policy applies to staging and production data managed by RugBoost in:
- Supabase Postgres tables (application operational records)
- Supabase Storage objects (generated PDFs and media artifacts)
- CI artifacts generated by scheduled readiness/reliability workflows

## Data-class retention policy

| Data class | Primary storage | Retention window | Deletion mode | Notes |
|---|---|---|---|---|
| Operational communication events (`communication_events`) | Postgres | 365 days | Rolling monthly purge | Preserves one-year traceability for support and incident review. |
| Payment attempts (`payment_attempts`) | Postgres | 730 days | Rolling monthly purge | Two-year window for billing disputes and reconciliation. |
| Pickup/check-in photo evidence (`pickup_photos`, `checkin_photos`) | Postgres + Storage | 365 days | Rolling monthly purge + object cleanup | Keep DB row + blob retention aligned. |
| Invoice PDF artifacts (`invoice-pdfs` bucket) | Supabase Storage | 2555 days (7 years) | Rolling quarterly purge | Long-term financial record retention target. |
| Release/readiness CI artifacts (`artifacts/*`) | GitHub Actions artifacts | 90 days | Platform TTL | Extend by copying to durable storage when required for audits. |
| Authentication and role-scope smoke logs | Artifacts + release evidence docs | 180 days | Rolling monthly purge | Minimum window for release investigations. |

## Compliance operating rules
1. Purges must be scheduled and documented; no ad-hoc bulk deletion in production.
2. Purge jobs must write a summary record (timestamp, table/bucket, deleted count).
3. Any legal hold or active incident overrides purge schedules for affected records.
4. Policy exceptions require an engineering + operations approval note in release evidence.

## Enforcement plan
1. Add scheduled SQL + storage purge jobs for each policy class.
2. Add dry-run mode for purge jobs in staging before production enablement.
3. Attach monthly purge summaries to release evidence package.
4. Review and update retention windows quarterly.

## Phase 3.4 validation gate
**Complete for baseline policy definition:** retention windows are documented for required data classes and linked in release operations docs.
Implementation of purge automation is tracked as a follow-on hardening task.
